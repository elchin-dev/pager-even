## Промпт A. Режимы Urgent / All

```
Прочитай AGENTS.md и docs/SPEC.md (§2.0 «Режимы»). Реализуй режимы ленты.
server:
- Таблица user_settings (user_id PK, feed_mode 'urgent'|'all' default 'urgent', voice_enabled default 1,
  conflict_alerts default 1, created_at, updated_at) + миграция. GET/PUT /api/settings (zod).
- GET /api/inbox?mode=urgent|all (по умолчанию из user_settings):
  urgent = priority='urgent' ИЛИ (priority='needs_reply' И есть конфликт с календарём); только answerable (есть черновики);
  all = все status='new' из подключённых чатов по времени, urgent помечены флагом.
  Ответ: {mode, counts:{urgent, all}, items:[...]}.
plugin:
- Шапка Inbox: "URGENT · 2" или "ALL · 9 (2!)". В режиме all срочные строки начинаются с "!".
- Пункт меню "Mode: Urgent/All" переключает режим (PUT /api/settings) и перестраивает Inbox.
- Пустое состояние Urgent: "No urgent · 7 in All" (подсказка, что есть другие сообщения).
Тесты на фильтрацию обоих режимов.
```
**Проверка:** напиши себе одно срочное и два обычных сообщения → Urgent показывает 1, All показывает 3; переключение через меню работает и сохраняется после перезапуска.

## Промпт B. Диктофон → голосовое сообщение

```
Реализуй диктофон: долгий тап на Card → запись → отправка как голосовое сообщение от имени пользователя.
Без расшифровки и без ИИ.
plugin:
- На Card: sysEvent LONG_PRESS → bridge.audioControl(true, Glasses) (сверь имена с .d.ts SDK),
  экран "● REC 0:03 · release to stop" (таймер через textContainerUpgrade раз в секунду).
  LONG_PRESS_RELEASE → audioControl(false). Лимит 60 с (автостоп).
- Дубль в меню: "Record voice" → тап начинает запись, тап останавливает (на случай, если ОС заберёт долгий тап).
- Буфер PCM (s16le, 16 kHz, mono) → WAV (44-байтный заголовок, src/lib/wav.ts).
- Что после остановки записи зависит от длительности (пороги в конфиге):
  • < 0.7 с → молча отменить, "Too short" на 1 с (явно случайное касание);
  • 0.7–2 с → БЕЗ таймера, экран подтверждения: "Voice 0:01 · short" / список "Send" / "Discard";
  • 2–30 с → экран "Voice 0:07 · sending in 3 · 2×tap cancel" (переиспользуй окно отмены);
  • > 30 с → БЕЗ таймера, экран подтверждения: "Voice 0:42 · long" / список "Send" / "Discard".
  На экране подтверждения тап по "Send" отправляет, "Discard" или двойной тап удаляют запись. Автоотправки нет.
  Отправка: POST /api/msg/:id/voice (Content-Type: audio/wav).
server:
- POST /api/msg/:id/voice: лимит тела 4 МБ, проверка владельца сообщения;
  ffmpeg: WAV → OGG/Opus (-c:a libopus -b:a 24k -ac 1 -ar 48000), через child_process со stdin/stdout, без временных файлов;
  sendVoice(chat_id, voice, {business_connection_id, duration}) через grammY (InputFile из Buffer).
  Статус сообщения replied, запись в actions (type 'voice', длительность, без аудио).
  Аудио нигде не сохранять.
- Dockerfile: установить ffmpeg (apt-get install -y ffmpeg). Health-check проверяет `ffmpeg -version` при старте и логирует результат.
- Если ffmpeg/отправка упали → {error:'voice_failed'}; на линзе "Voice not sent · tap retry".
```
**Проверка:** запись 1 с и 40 с → появляется подтверждение без таймера, Discard ничего не отправляет. Затем в симуляторе с микрофоном (`--aid`) держи долгий тап 5 с → у собеседника в Telegram приходит голосовое **от тебя** длительностью ~5 с и нормально воспроизводится.

## Промпт C. Конфликты с календарём («вы заняты»)

```
Реализуй детектор конфликтов (docs/SPEC.md, Флоу D «Конфликты»).
server:
1) Расширь zod-схему триажа: intent добавь 'task'; новое поле
   when: { start: ISO | null, end: ISO | null, allDay: boolean, text: string } | null —
   ИИ извлекает дату/время из сообщения («завтра в 3», «в четверг утром», «до пятницы») относительно
   текущего времени и таймзоны пользователя (users.tz, по умолчанию Asia/Tashkent). Если времени нет → null.
   Длительность по умолчанию 60 мин. Фолбэк buildFallbackTriage → when=null.
2) Если when.start есть и Google подключён: запроси события на этот интервал (± 0) →
   conflict = {title, start, end} первого пересечения или null. Сохрани в ai_json.
3) Черновики при конфликте (ИИ получает conflict + 2 свободных слота рядом):
   "I'm busy then (until 16:00). 17:00 works?" (+cal на слот), "Can we do tomorrow 11:00?" (+cal), "Let me check and get back".
   Без конфликта для schedule/task: первый черновик "Yes, 15:00 works" с +cal (создаёт событие на when).
   Для task с дедлайном без конфликта: черновик "Will do by Fri" с +cal (событие-напоминание).
4) Уведомление: при обнаружении конфликта бот пишет пользователю в личку бота (не собеседнику!):
   "⚠ Aziz: meeting Thu 15:00 — you have 'Standup' 15:00–16:00." (одно сообщение на входящее; настройка conflict_alerts).
   Это работает как пуш на телефон, даже если плагин закрыт.
5) SSE: событие "conflict" → плагин показывает баннер.
plugin:
- Строка Inbox с конфликтом: "⚠ Aziz  Meet Thu 15:00?".
- Card: шапка "Aziz · ⚠ busy", вторая строка "You: Standup 15-16", дальше черновики.
- Если плагин открыт на другом экране, при SSE "conflict" на 3 с показать баннер "⚠ Aziz · busy Thu 15:00" и вернуть экран.
Тесты: парсинг when фиксированными примерами (мок LLM только в тестах), пересечение интервалов, выбор слотов.
```
**Проверка:** создай в календаре событие завтра 15:00–16:00; со второго аккаунта напиши «Созвонимся завтра в 15:30?» → в боте приходит предупреждение, на линзе ⚠ и черновик с другим временем; тап → ответ ушёл и событие создано на новый слот.

## Промпт D. Catch-up бриф и ближайшая встреча

```
1) GET /api/brief → {nextEvent:{title,start}|null, missed:{total, urgent, people:[3 имени]}, line1, line2}
   line1/line2 — ИИ-сводка ≤ 40 символов каждая (латиница): "3 need reply · Aziz waits on KP",
   "Next: Standup 15:00 (in 12m)". Кэш 60 с.
2) Plugin: при открытии плагина, если с прошлого открытия прошло > 30 мин и есть новые — экран Brief
   (2 строки + "tap → inbox"), иначе сразу Inbox.
3) Шапка Inbox справа: "· 15:00 Standup" если событие в ближайшие 60 мин.
```
**Проверка:** закрой плагин, получи 3–4 сообщения, открой через 30+ минут (или временно поставь порог 1 мин) → бриф с правильными числами.

## Промпт F. Продакшен, staging, хостинг плагина

```
Подготовь проект к публичному использованию и проверке жюри.

4) Безопасность и устойчивость: rate limit /api/* (60/мин на устройство), лимит ИИ-вызовов на пользователя в сутки,

5) README: раздел "Try it in 3 minutes" для жюри:
   а) симулятор: npx evenhub-simulator https://<prod>/app ; б) .ehpk / QR для реальных очков;
   в) пройти онбординг из 3 шагов. Отдельно: "Self-hosting" для разработчиков (env, Railway, BotFather, Google Cloud).
```
**Проверка:** с чистой машины по README жюри запускает симулятор на прод-URL и подключает свой Telegram без единого ключа.
